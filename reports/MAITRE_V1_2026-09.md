## 1. Architecture — final data flow

```
COLLECT                     Windows Defender, Windows Event Log, process
                             inspection, file hashing/signature, persistence
                             enumeration (registry/startup/tasks/services),
                             Observateur (passive network/process metadata)
   │
   ▼
NORMALIZE                   Each source's own pure converter
                             (*ToSecurityEvent) → buildSecurityEventRow()
                             (maitre-models.js) — the ONE validated insert
                             path into maitre_events. No bypass exists.
   │
   ▼
CORRELATE                   Deterministic rules only (maitre-correlation.js)
                             — time-windowed, deduplicated, severity
                             escalation bounded by fixed rule logic. Zero
                             LLM involvement in this step.
   │
   ▼
INCIDENT                    createIncidentFromCorrelation() — one incident
                             per correlation match, timeline-bounded,
                             evidence-linkable, status machine enforced by
                             isValidIncidentTransition().
   │
   ▼
ANALYZE (optional)          Local analyst (maitre-analyst.js): deterministic
                             by default, Ollama-local if configured. Never
                             writes severity/status. Facts/Hypotheses/
                             Unknowns/Review-suggestions strictly separated;
                             review suggestions filtered against an
                             executable-shape denylist.
   │
   ▼
PROPOSE                     createActionProposal() — closed 8-action
                             allowlist, level assigned server-side from a
                             fixed table, never client-chosen.
   │
   ▼
POLICY                      evaluateActionPolicy() — ALLOW / CONFIRM / DENY,
                             LEVEL 2 always requires confirmation, LEVEL 3
                             requires confirmation + (for HOST_ISOLATION
                             specifically) strengthened confirmation.
   │
   ▼
APPROVE                     createApprovalRequest() → approveProposal() —
                             cryptographic hash binding (proposal/target/
                             parameters), one-time consumption, TTL expiry,
                             explicit strengthened-confirmation gate.
   │
   ▼
EXECUTE                     executeApprovedAction() — the ONE entry point;
                             re-validates policy/approval/TOCTOU/level
                             fresh from the current DB state immediately
                             before touching the OS. Semantic dispatch
                             table, 8 named executors, no generic command
                             path.
   │
   ▼
AUDIT                       maitre_action_runs — one row per execution
                             attempt, bounded+redacted result metadata,
                             never SUCCEEDED on a partial/unverified state.
   │
   ▼
UI                          MAÎTRE Studio (7 tabs) + Command Center widget
                             + Feature Registry entry — exposes exactly the
                             above pipeline, adds no new capability.
```

## 4. Policy engine

Three levels, re-verified via `test-maitre-policy.mjs` (part of the 50/50 policy+approval suite this session):

- **LEVEL 1** (`COLLECT_EVIDENCE`, `SCAN_WITH_DEFENDER`): `ALLOW` decision, executes immediately after proposal, no approval step.
- **LEVEL 2** (`TERMINATE_PROCESS`, `QUARANTINE_WITH_DEFENDER`, `BLOCK_REMOTE_IP`, `DISABLE_PERSISTENCE_ENTRY`): `CONFIRM` decision, requires an explicit approval before execution.
- **LEVEL 3** (`HOST_ISOLATION`, `RESTORE_HOST_NETWORK`): `CONFIRM` decision; `HOST_ISOLATION` additionally requires `strengthened_confirmation` (its own policy `requirements` array states this), `RESTORE_HOST_NETWORK` does not (its policy `requirements` lists only `user_confirmation` — a real inconsistency in `maitre-approval.js`'s enforcement was found and fixed in MA-11: the gate previously checked a blanket `level === 3` instead of the actual per-action requirement, which would have incorrectly demanded strengthened confirmation for restore too).

The level is never client-chosen — `validateActionInput()` always looks it up server-side from the closed `ACTION_LEVELS` table, confirmed by a dedicated route test sending `level: 3` in a LEVEL-1 proposal body and observing the response still reports `level: 1`.

## 5. Approval security

Re-verified this session (50 policy+approval tests + 36 route tests, all passing):

- **Proposal hash**: SHA-256 of `{incidentId, actionType, target, parameters}` via canonical (sorted-key) serialization.
- **Target/parameter hash binding**: approval stores its own hashes at request time; `validateApproval()` re-derives fresh from the current action row on every check.
- **Expiration**: 5-minute TTL, checked and auto-transitioned to `EXPIRED` on any read past expiry.
- **One-time use**: `consumeApproval()` moves status to `CONSUMED`; a second use fails via `validateApproval()`'s own `CONSUMED` check.
- **Replay protection**: confirmed by route test — executing the same action twice with the same approval fails on the second attempt.
- **Tampering protection**: a rejected-then-reapproved approval fails (`approval_not_pending`).
- **Wrong action / wrong target / wrong incident**: `validateApproval()`'s `expectedActionId`/`expectedIncidentId` checks, plus the hash re-derivation, catch any mismatch — confirmed by a dedicated "wrong incident" route test.

## 10. Persistence remediation

## 11. Host isolation (MA-10)

Certified this session via 20/20 passing tests (`test-maitre-host-isolation.mjs`) plus live confirmation of zero real isolation rules on this machine:

- **Strengthened confirmation**: hard-gated at `approveProposal()`, never bypassable.
- **Rollback state persisted first**: `createIsolationRollbackState()` inserts the `maitre_isolation_state` row (status `PENDING`) before any firewall change; insert failure denies the isolation before touching the OS.
- **Transactional apply**: 4 rules created one at a time, progress persisted after each success, best-effort rollback of already-created rules on any failure.
- **Partial failure handling**: distinct `PARTIAL_FAILURE` status, never silently folded into `FAILED` or `SUCCEEDED`.
- **Loopback preserved**: by construction, not by Block/Allow ordering — every Block rule's `RemoteAddress` explicitly excludes `127.0.0.0/8` (IPv4) and is scoped to global-unicast-only for IPv6 (trivially excluding `::1`). This design was chosen specifically because MA-10's own audit found Windows Firewall's documented precedence is "explicit Block always beats explicit Allow, regardless of specificity" — an Allow-loopback-plus-Block-Any design would have been unsafe.
- **Docteur local access preserved**: verification step re-checks a live loopback HTTP probe to cortex-server's own health endpoint after applying rules; failure triggers full rollback.
- **Foreign firewall rules untouched**: every mutating call is `-DisplayName`-scoped; restore additionally re-checks that every rule name in its own rollback record matches `Docteur-MAITRE-Isolation-<this-action's-own-id>-` before removal.
- **No adapter disable, no DNS/routes/proxy changes**: confirmed via a dedicated static-safety test scanning for `Disable-NetAdapter`, `Set-DnsClientServerAddress`, `New-NetRoute`, `Set-WinHttpProxy`, etc. — zero matches.
- **Restore exact ownership + idempotency**: a second restore call on an already-`RESTORED` state returns `ALREADY_RESTORED` with zero new removal calls, verified by test.
- **Crash recovery detection**: `detectActiveIsolationOnStartup()` reads only the persisted DB state, never auto-restores — the decision remains the user's via the ordinary proposal/approval flow.

## 29. Honest known limitations (MAÎTRE V1)

- **Windows-first**: every OS-touching inspector/executor is Windows-only; non-Windows platforms degrade to `NOT_SUPPORTED`/`UNKNOWN`, never a crash, but MAÎTRE provides no incident-response capability on macOS/Linux.
- **Defender quarantine `NOT_SUPPORTED`**: `Remove-MpThreat` has no per-detection targeting parameter in the available API — remediating via Defender would mean remediating ALL active threats system-wide, judged unsafe to expose.
- **QuickScan/FullScan `NOT_SUPPORTED` V1**: unbounded scan duration (QuickScan measured ~50s on the dev box; FullScan is unbounded) is incompatible with a bounded request/response model.
- **Admin privileges required for some actions**: firewall rule creation, persistence disable, and host isolation all require elevation; MAÎTRE never auto-elevates — these fail cleanly with `access_denied` when run non-elevated.
- **Real host isolation never tested on a real machine**: by explicit mission mandate across MA-10, MA-11, and MA-12 — all isolation logic is validated via mocked exec injection plus live read-only capability probes, never a genuine `New-NetFirewallRule` block applied to this or any development machine.
- **IPv6 isolation scope is conservative**: scoped to global-unicast-only (`2000::/3` and above), not a precise "all IPv6 except `::1`" exclusion — link-local (`fe80::/10`) and unique-local (`fc00::/7`) IPv6 traffic is not blocked by the current isolation rules, a narrower containment guarantee than the IPv4 rules provide.
- **Local analyst's Ollama path is optional and not exhaustively live-tested**: the deterministic fallback is what's actually exercised in automated tests; a real local Ollama model's output has been tested for structural validation (schema enforcement, executable-shape filtering) but not exhaustively for output quality.
- **Retention scheduler not wired**: `purgeSecurityEventsOlderThan()` exists but is called by nothing outside its own test — data grows unbounded in `maitre_events`/`maitre_incidents`/etc. until a future phase adds a scheduler.
- **No kernel/driver/rootkit inspection**: MAÎTRE operates entirely at the user-mode Windows API level (WMI, Event Log, registry, Defender's own reporting) — it has no kernel-level visibility, cannot detect a kernel rootkit, and makes no such claim.
- **No forensic chain-of-custody guarantee**: evidence SHA-256 hashes exist for tamper-evidence/dedup purposes only, explicitly documented as not a legal forensic chain-of-custody mechanism.
- **No guaranteed malware detection, no zero-false-positive claim**: MAÎTRE surfaces deterministic correlation signals and Defender's own detections; it makes no claim of comprehensive malware detection coverage, and both Observateur's and MAÎTRE's own documentation explicitly warn that a new/unusual observation is not automatically malicious.
